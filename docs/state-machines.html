Nanospot · frontends/nanoui + core

Floodlight state machines

Nanospot is the Zig rewrite of Floodlight: a Spotlight-style search panel on ⌥Space and a clipboard board on ⌥⇧C, over a Zig file index. Eleven state machines decide what the panel shows, what it remembers, and what Return does. Two are explicit enums. Nine live in flags, arenas and timers.

Each plate shows the machine, why the product needs it, the code that holds the state, and drill-downs for invariants, the full transition table, and where to read next. The written source of truth is docs/state-machines.md.

How turns interleave

The panel never acts in the frame where you press Return. It records the action and the shell runs it on a later main-queue turn. Anything else queued in between (a clipboard capture, an index swap, the file-rows timer) can change state first. The ⌘K menu runs a nested loop that drains all of them while it is open.

Action handoff

implicittwo turnsfinding 1 fixed

Business context: Return, ⌘C and a double click name one result or clipboard entry. Whatever the user saw selected must be what gets opened or pasted, even if a new copy arrives or the index swaps before the shell acts.

stateDiagram-v2
  [*] --> none
  none --> asked : ask copies the action into action_arena
  asked --> asked : a second ask replaces it
  asked --> none : Panel.hide clears pending
  asked --> applying : applyPanel on a later turn
  applying --> none : action run, then settle
  
frontends/nanoui/src/panel.zig:888fn ask(p: *Panel, a: Action) void {
    p.recordActionQuery(a);
    _ = p.action_arena.reset(.retain_capacity);
    p.pending = ownedAction(p.action_arena.allocator(), a) catch |err| {
        std.log.err("action: {s}", .{@errorName(err)});
        return;
    };
    p.hooks.request(p.hooks.ctx);
}
Invariants
  • The bytes an action names stay valid from ask to the end of its apply.
  • One slot: a second ask before the apply replaces the first. The second apply only resizes.
  • Panel.hide clears pending. An apply that finds nothing only resizes.
What went wrong before

The action held slices into the result list's arena. A refresh between the ask and the apply reset that arena and reused it. The regression test found the paste would write a copy from another app, instead of the entry the user chose.

implicit0 ms timerfinding 7 open

Business context: each keystroke must publish within 10 µs. When the file search is slower than 4 ms, apps answer at once and file rows land on the next turn, so typing never stalls.

  idle --> due : answer over budget, timer queued once
  due --> due : more keystrokes, no second timer
  due --> idle : timer, still search and same text, rows with files
  due --> idle : timer, board mode or text changed, files dropped
  
frontends/nanoui/src/panel.zig:544pub fn landFiles(p: *Panel) void {
    if (!p.files_due) return;
    p.files_due = false;
    const text = p.field.text();
    if (p.mode != .search or !std.mem.eql(u8, text, p.list.answered())) return;
    if (p.list.selected != 0) p.list.markStale();
    _ = p.answer(text, true) catch |err| return p.failSearch(err);
    p.completion = p.computeCompletion();
}
Open finding

The flag clears before the mode check. If the timer runs after a switch to the board, the retained search restores later without file rows, and refresh sees an unchanged query. Narrow, because the timer is 0 ms.

File index rebuild

explicit protocolreal threads, atomicsno bug

Business context: the last index opens at launch, so search works at once. A fresh scan of the home folder runs on its own thread and swaps in when it finishes. Requests during a scan cost one more scan, never a lost one.

stateDiagram-v2
  [*] --> idle
  idle --> scanning : rebuild, requested + 1, wins running
  scanning --> scanning : another rebuild, requested + 1, returns at once
  scanning --> ready : scan done, running false, notify
  ready --> scanning : requested above 0
  ready --> idle : requested is 0
  ready --> adopted : main thread adopt swaps the index
  
core/src/file_index.zig:97pub fn rebuild(fi: *FileIndex, notify: Notify) void {
    _ = fi.requested.fetchAdd(1, .seq_cst);
    while (fi.running.cmpxchgStrong(false, true, .seq_cst, .seq_cst) == null) {
        _ = fi.requested.swap(0, .seq_cst);
        const outcome = fi.buildOnce();
        fi.running.store(false, .seq_cst);
        notify.ready(notify.ctx, outcome);
        if (fi.requested.load(.seq_cst) == 0) return;
    }
}
Invariants
  • At most one scan runs at a time.
  • No request is lost: each caller adds before it tries to run, and the runner reads after it clears running.
  • ready holds at most one finished index. A newer one closes the older.
  • busy() is true from a request until the last scan notifies.
