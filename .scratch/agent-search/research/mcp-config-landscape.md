## 2. Schema notes / quirks worth encoding in an indexer

- **stdio vs remote is universal** but the discriminator field differs: Claude Code/Codex/Crush/droid/omp use `type` (`"stdio"|"http"|"sse"[|"ws" for Claude Code]`, defaulting to stdio when omitted for most); opencode uses `type:"local"|"remote"`; pi infers from presence of `url` vs `command`.
- **Enable/disable flags** are inconsistent: `enabled:false` (omp, opencode), `disabled:true` (Crush, droid), `enabled = false` (Codex TOML), allow/deny-list arrays (omp `enabledServers`/`disabledServers`, Gemini `mcp.allowed`/`mcp.excluded`, Claude Code's per-project `enabledMcpjsonServers`/`disabledMcpjsonServers`).
- **Tool-level filtering** exists in several: pi (`directTools`, `excludeTools`), Crush (`disabled_tools`), droid (`disabledTools`), amp (glob patterns like `mcp__metabase__*` on the CLI tool-allow flag). An indexer that only records *servers* will miss that some agents suppress individual tools per server.
- **Approval/trust gates** matter for "what's actually active": Claude Code project-scope servers sit `⏸ Pending approval` until the workspace is trusted; amp workspace servers need `amp mcp approve`; droid's project/folder scope is subject to an org MCP policy. A static config parse will over-report servers that are declared but not yet approved/active.
- **Secrets live inline** in most schemas (`env` objects for stdio, `headers` objects for remote — commonly `Authorization`/`X-Api-Key`). Any indexer must redact values by key-name heuristics (`key|token|secret|auth|password` in the field name) — note that Claude Code's `headers` values (e.g. a raw `X-Goog-Api-Key`) are **not** caught by an `env`-only redaction filter, so redact by object depth/key pattern, not just the `env` key name.
- **Two agents in this list (pi/omp) share a runtime lineage** ("oh-my-pi") but have diverged schemas — pi supports `directTools`/`excludeTools`, omp's published schema does not. Don't assume parity between them.
- **Claude Desktop has two independent declaration surfaces** — raw `claude_desktop_config.json.mcpServers` and installed DXT extensions (`Claude Extensions/<id>/manifest.json`) — an indexer must scan both, and DXT manifests carry their own static `tools` array (see below).

## 3. Tool enumeration: static cache vs. live probe

This varies a lot by agent — the honest answer is "mixed, and mostly live":

- **Claude Code**: no on-disk cache of full tool JSON-schemas was found in `~/.claude.json` or `~/.claude/settings.json` on this machine (`mcpContextUris` per project is empty and appears to track referenced MCP *resource* URIs, not tool lists; `mcp-needs-auth-cache.json` only tracks which servers need auth). However, **official docs confirm an in-session discovery cache exists** (Claude Code ≥ v2.1.221): a previously-used remote (HTTP/SSE) server can show `cached 2h ago · connects on first use · 5 tools` in `/mcp` — Claude Code reuses a prior session's `tools/list` result instead of reconnecting at startup, and only makes a live connection on first tool call. This is disableable via `MCP_DISCOVERY_CACHE=0`. The exact on-disk storage location for this cache was not identified among the human-readable keys of `~/.claude.json` — likely an internal, undocumented store. Stdio servers are not mentioned as cached this way (they're cheap to spawn and re-`tools/list`).
- **Claude Desktop / DXT extensions**: **statically cached, in effect** — an installed extension's `manifest.json` ships a top-level `tools` array (`{name, description}` pairs) written by the extension author at package time. This is available without spawning the server at all, though it's author-declared, not guaranteed to be byte-identical to a live `tools/list` (schema/`inputSchema` details are not in the manifest, only name+description).
- **pi**: has a genuine, verified on-disk tool-schema cache — `~/.pi/agent/mcp-cache.json`, keyed `servers.<name>.{configHash, tools:[{name, description, inputSchema}]}`. The `configHash` is clearly there to invalidate the cache when the server's config entry changes. This is the most complete example in this survey: full `inputSchema` per tool, cached statically, keyed by a hash of the declaring config.
- **omp, Crush, opencode, Codex, amp, droid, Gemini CLI**: no on-disk static tool-schema cache was found on this machine, and none of the docs fetched mention one (droid's docs explicitly frame tool listing as requiring a live connection: "every tool the server reports is loaded except the listed names"). These agents appear to require actually spawning/connecting to the server and calling `tools/list` to enumerate tools — config parsing alone tells you *which servers are declared*, not what tools they expose.

## 4. Recommendation for a Floodlight catalog indexer

1. **Static-parse configs for server inventory** (name, transport, command/url, enabled/disabled, scope) — this is cheap, safe (no process spawns, no network), and covers "which MCP servers does each agent have" for all 10 agents using the paths/schemas in the matrix above. Redact secret-shaped fields (`env`, `headers`, `auth`, anything key-matching `key|token|secret|password`) before persisting or displaying.
2. **Respect approval/enable state** when deciding whether a declared server counts as "active": check Claude Code's `enabledMcpjsonServers`/`disabledMcpjsonServers` + trust dialog state, amp's workspace approval, droid's org policy, and each agent's own `enabled`/`disabled` flags — otherwise the catalog overcounts servers that are configured-but-inert.
3. **Only probe live (spawn + `initialize` + `tools/list`) when you actually need per-tool metadata** (name, description, input schema) for search/ranking, and even then prefer reading an existing cache first:
   - Check `~/.pi/agent/mcp-cache.json` (and the equivalent under `~/.omp/agent` if it turns out to exist there too — not confirmed on this machine) before spawning a pi/omp-declared server.
   - For Claude Desktop, read the DXT `manifest.json`'s `tools` array first — it's free and matches remote-cache class information (name+description, no schema).
   - For everyone else (Claude Code stdio servers, Codex, Crush, opencode, droid, amp, Gemini CLI), there is no reliable static tool cache to read, so live probing is the only way to get real tool lists — budget for spawn cost (stdio) or a network round trip + OAuth (remote), and cache the indexer's *own* results keyed by a hash of the server's declared config (command+args+env-keys, or url+headers-keys) so re-indexing is cheap until the config changes — this mirrors what pi already does internally and is the pattern to copy.
   - Treat remote servers specially: they may require OAuth (amp, droid, Claude Code connectors) before `tools/list` succeeds — a naive prober needs to detect and skip/flag auth-gated servers rather than hang or error.
4. **Watching for changes**: use filesystem watches (FSEvents on macOS) on the specific files in the matrix, not whole directories — most of these live inside large, frequently-churned state directories (session logs, sqlite WAL files, etc.) where a directory-level watch would be noisy. Key files to watch: `~/.claude.json`, `~/.claude/settings.json`, every repo's `.mcp.json`/`.claude/settings.json`; `~/Library/Application Support/Claude/claude_desktop_config.json` + `Claude Extensions/*/manifest.json`; `~/.codex/config.toml`; `~/.config/crush/crush.json` + `~/.local/share/crush/crush.json` (note: on this machine the former is a **symlink into the Nix store** — watch the resolved target, not just the symlink path, or you'll miss changes made by `home-manager switch`); `~/.config/opencode/opencode.json` + per-project `opencode.json(c)`; `~/.pi/agent/mcp.json` + `~/.pi/agent/extensions/*.json`; `~/.omp/agent/mcp.json`; `~/.factory/mcp.json` (user) + any ancestor/project `.factory/mcp.json`; `~/.config/amp/settings.json` (also Nix-symlinked here) + per-workspace `.amp/settings.json`; `~/.gemini/config/config.json` and `~/.gemini/config/mcp_config.json` (and re-check `~/.gemini/settings.json` since this machine shows a docs/reality mismatch from a settings migration). Debounce writes (several of these tools rewrite the whole file on every `mcp add`/toggle) and re-run only the static parse step on change; only re-probe live tool lists when a server's own config sub-object actually changed (hash comparison), not on every file touch.
5. **Don't conflate adjacent-but-different mechanisms**: Codex "Apps"/connectors (`[apps.connector_<id>...]`) are a distinct ChatGPT integration surface, not raw MCP; Claude Desktop DXT extensions are MCP-backed but packaged/installed differently from hand-edited `mcpServers` JSON; pi's `extensions/*.json` files are a separate declaration path from its own `mcp.json`. A catalog that only understands the "obvious" `mcpServers`/`mcp_servers` object per agent will under-count real, running MCP servers for Codex, Claude Desktop, and pi specifically.
